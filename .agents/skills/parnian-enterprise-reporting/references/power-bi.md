# Power BI

Record the target product, exact build, Desktop edition, compatibility level, storage mode, and authorized deployment path. For Power BI Report Server, use the compatible Desktop for Report Server release and verify supported sources, refresh, security, visuals, and project formats for the exact build. Use validated PBIX workflows where project formats lack support. Keep on-premises deployments on premises unless cloud use is explicitly approved. Power BI Service requires an explicit request. Check Microsoft's current [Report Server feature comparison](https://learn.microsoft.com/en-us/power-bi/report-server/compare-report-server-service) and [release notes](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new).

- Define each fact's grain and use dimensions with unique keys, preferably one-to-many single-direction relationships. Resolve many-to-many with a grain-aware bridge when justified. Document inactive relationships and test filter propagation.
- Favor explicit measures. Account for row and filter context, context transition under CALCULATE, subtotal behavior for ratios and distinct counts, and BLANK semantics. Model a contiguous date dimension with Jalali display and calendar-period keys. Define comparable periods before choosing time intelligence functions.
- In Power Query, assign types early, push filters and projections to the source, and verify query folding with supported diagnostics. Compare Import and DirectQuery against latency, cardinality, refresh, and security requirements. Use incremental refresh only after confirming support for the target and verifying partition predicates and folding.
- Use realistic cardinalities and measure slow visuals or queries with available profiling tools. Reduce unnecessary columns and visuals, and document time budgets. Verify row-level security as restricted users across detail, totals, drill-through, and exports. Record publish and rollback steps for the approved target.
- Test supported PBIP/PBIR and TMDL artifacts in the target client before deployment. Keep source changes and deployment separately reviewable.
